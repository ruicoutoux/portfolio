01 The Problem

Large enterprise customers have different business lines which depend on different non-functional requirements — security boundaries, compliance requirements, deployment cadences. For example a company might have a set of internal apps, plus a set of customer-facing ones. Portfolios allow platform admins to create meaningful boundaries between these groups, so that each can be managed independently at scale.

The core pain: Platform admins had no way to create meaningful boundaries between application groups. One compliance boundary affected everything — or nothing.

The original ODC model — all applications sharing a single flat namespace within the Organisation

02 Constraints & Context

From a UX perspective, introducing Portfolios meant restructuring a core mental model that existing users already relied on. Every surface in the product — navigation, settings, monitoring consoles, the IDE — had to reflect the new hierarchy without breaking the existing experience.

Different concept live at different abstraction levels

The critical constraint: some concepts belong inside a Portfolio (apps, stages), while others remain at the Organisation level (global settings, billing). Users, while belonging to the Organization, are assigned to portfolios. Making that asymmetry navigable — without users ever having to consciously think about scope — was the central design challenge.

From the structural model I derived the full scope of change: new configuration and management screens for Portfolios; updates to every existing screen that referenced Applications or Stages; a Portfolio selector pattern for cross-portfolio views; and a full navigation redesign.

End-to-end product analysis: Knowing the conceptual model wasn't enough; I had to map its UX impact across the entire product. I audited every flow, navigation entry, and instance to identify imapcts of the conceptual change, to reclassify them under the new hierarchy. This meant holding both the conceptual logic and full product surface in mind at once—determining what changed, where it changed, how it changed, and in what order to preserve a coherent experience for existing users.

04 The Navigation Problem

One of the biggest design challenges was the navigation. With two distinct scopes now coexisting, the side navigation had to answer a question users would never consciously ask: is this page for my Portfolio, or for my entire Organisation?

First approach(es) (discarded): A single level navigation, then a strict two-level navigation hierarchy — first level for Portfolio-scoped items, second level for Organisation-scoped items. Clear in theory. User research proved it didn't match how admins actually think about their work.

First navigation approach (left: low fi; right: high fi) — structurally correct, but failed in user research on task completion and orientation time

Final navigation model — scope by task, not by architectural correctness

05 The Hard Trade-off

Key decision
Familiarity over structural purity

A structurally "correct" navigation would mirror the hierarchy exactly — Portfolio items in the first level, Organisation items in the second level, two distinct zones. Architecturally clean. Cognitively wrong.

User research backed the call to discard it. Admins failed tasks and took longer to orient. The final model preserves familiar task-based navigation and surfaces scope at the page level — not in the structure. Admins never have to think about it.

06 Outcome

The conceptual model, use cases, flows, and low-fidelity designs were completed and handed off to the engineering team, with an experience that covers the expected outcomes and use cases. Hi-fidelity execution was deliberately delegated to a peer in favour of parallel work on ALM and A2A configuration — a deliberate scope trade-off, not a gap.
