Portfolios: Restructuring How Enterprises Organise at Scale

OutSystems' flat application model couldn't support enterprises that need to segregate apps by different non-functional requirements. I defined a new structural layer — Portfolios — and redesigned the platform's navigation model around it.

01 The Problem

Enterprise platform admins manage applications with very different non-functional requirements — security boundaries, compliance requirements, deployment cadences. The flat model forced everything into the same bucket, with no way to segregate, govern, or manage apps independently at scale.

The core pain: Platform admins had no way to create meaningful boundaries between application groups. One compliance boundary affected everything — or nothing.

02 Constraints & Context

This wasn't a new screen or a feature addition. Introducing Portfolios meant restructuring a core mental model that existing users already relied on. Every surface in the product — navigation, settings, monitoring consoles, the IDE — had to reflect the new hierarchy without breaking the existing experience.

The critical constraint: some concepts belong inside a Portfolio (apps, pipelines, stages), while others remain at the Organisation level (users, billing, global settings). Making that asymmetry navigable — without users ever having to consciously think about scope — was the central design challenge.

From the structural model I derived the full scope of change: new configuration and management screens for Portfolios; updates to every existing screen that referenced Applications or Stages; a Portfolio selector pattern for cross-portfolio views; and a full navigation redesign.

End-to-end product analysis: Knowing the conceptual model wasn't enough — I needed to understand its UX impact on every single surface. I traced the structural change across the entire product: every screen, every navigation entry, every place where an Application or Stage was referenced had to be audited and reclassified under the new hierarchy. This required holding both the conceptual logic and the full product surface simultaneously — knowing not just what changed, but where it changed, how it changed, and in what order it needed to change to remain coherent for existing users.

04 The Navigation Problem

The hardest design problem wasn't the new Portfolio screens — it was the navigation. With two distinct scopes now coexisting, the side navigation had to answer a question users would never consciously ask: is this setting for my Portfolio, or for my entire Organisation?

First approach (discarded): A strict two-level navigation hierarchy — first level for Portfolio-scoped items, second level for Organisation-scoped items. Clear in theory. User research proved it didn't match how admins actually think about their work.

05 The Hard Trade-off

Key decision
Familiarity over structural purity

A structurally "correct" navigation would mirror the hierarchy exactly — Portfolio items above, Organisation items below, two distinct zones. Architecturally clean. Cognitively wrong.

User research backed the call to discard it. Admins failed tasks and took longer to orient. The final model preserves familiar task-based navigation and surfaces scope at the page level — not in the structure. Admins never have to think about it.

06 Outcome

The conceptual model, use cases, flows, and low-fidelity designs were completed and handed off to the engineering team. Hi-fidelity execution was deliberately deprioritised in favour of parallel work on ALM and A2A configuration — a deliberate scope trade-off, not a gap.
